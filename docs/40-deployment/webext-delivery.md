# WebExt 版本与分发

WebExt 是独立交付的浏览器 Peer，不属于 Module Federation Extension。Chromium 和 Firefox 共享 `apps/client-webext/package.json` 的版本，构建不同浏览器产物；不随 client-web、Core 或 MF Registry 的版本发布。

## 安装和手动更新

GitHub Release 使用 `webext-v<版本>` 标签。下载其中的 `inkcre-webext-<版本>-chrome.zip`，解压到长期保留的目录，在浏览器扩展管理页启用开发者模式并“加载已解压的扩展”。不要加载 ZIP 本身，也不要使用解压工具自动套出的外层目录：选择直接包含 `manifest.json` 的目录。

更新时先保留旧目录副本，将新版完整解压到同一目录，再在扩展管理页重新加载。不要通过卸载重装更新；卸载会删除该安装的本机数据。设置页标题显示实际安装版本。刷新已经打开的网页，让旧内容脚本退出。下载包不会自动更新，暂不自建更新服务器。

Firefox ZIP **未签名，仅供 `about:debugging` 临时加载**，不能作为正式持续安装包，也不能改成 `.xpi` 后宣称已签名。正式 Firefox 分发需要 Mozilla Add-ons 账号和签名；未签名前，不能承诺临时安装跨浏览器重启保留数据。现有固定 Gecko ID 是 `webext@inkcre.org`。

## 从早期 Chromium 安装迁移

固定公钥写入 manifest 后，解压目录变化不再改变 Chromium 扩展 ID。早期没有公钥的安装按路径生成另一 ID，浏览器不会把它的存储自动交给新身份。先完成一次数据转移，此后的固定身份版本按普通更新处理。

1. 从相同源码执行 `pnpm --filter @inkcre/client-webext zip:migration`。这是不带固定公钥的过渡构建，只用于早期安装的数据导出，不是正式发布包。保留旧目录副本后，将过渡构建放到原安装的**完全相同路径**，重新加载；确认信息库与待办仍在。不要把带固定公钥的正常构建直接覆盖到这个路径。
2. 在设置页暂停自动采集和运行中的导入，等待正在发送的工作结束，关闭其他扩展页面。展开“本机数据迁移”，导出文件；随后停用旧实例，不要卸载。
3. 在另一个目录加载正常固定身份构建，在空实例中迁入文件。已有连接、待办、导入或封存记录的实例会拒绝迁入，不合并或覆盖。
4. 核对信息库、待办和导入进度。点击“检查连接”重新授权数据库地址，重新启用需要的网站权限；书签、历史权限也需重新授予。重新加载新扩展后按需恢复采集与导入。不要同时启用承载相同 Peer 身份的旧、新实例。

文件保留 profile ID、连接及 Peer ID、完整待办材料（包括 PDF）、导入 checkpoint 和旧封存数据，不复制浏览器授予的权限。文件包含明文 JWT 密钥，应私下保管，不上传到聊天或 Issue。若迁移失败，停用新实例，旧实例的数据仍可恢复使用。

`zip:migration` 单独生成 `.output/chrome-mv3-migration` 与文件名带 `migration` 的 ZIP，不覆盖正常 `.output/chrome-mv3`。正式发布命令只使用正常构建，并拒绝缺少固定身份的包。

## 准备版本与产物

用户可见变更携带针对 `@inkcre/client-webext` 的 Changeset。复用工作区 Version PR 消费这些文件，更新版本和 changelog；不要手改生成的 manifest。重写首次交付使用 minor 变更意图，由 Version PR 将当前 `0.1.4` 准备为 `0.2.0`，不是仅合并功能 PR 就发布当前版本。

版本使用三段纯数字 SemVer，每段不超过 65535。不要以 `-beta` 后缀区分浏览器包：WXT 会把后缀从 manifest 版本中去掉，两个候选可能因此成为同一个浏览器版本。测试候选用来源提交区分，不冒充正式新版本。

在仓库根目录安装冻结依赖并提交源码后执行：

```sh
pnpm release:webext:build
pnpm release:webext:check
```

产物位于忽略的 `.webext-delivery/`：两个浏览器 ZIP、对应提交的仓库源码归档，以及记录来源提交、浏览器身份和资产 SHA256 的 `source.json`。本地命令不上传、不签名、不发布。InkUI 依赖由锁文件从公开的版本化 Release 下载，无需组织凭据；源码归档不包含依赖，尚未验证 AMO 独立重建审查。

`.github/workflows/webext-release.yml` 只选择当前受保护 main 上已生成 changelog、没有待消费 WebExt Changeset 的版本，构建并发布 GitHub Release。其他单元的 Changeset 不阻止 WebExt。手动重试必须指定当前 main 的确切提交。流水线先上传草稿并核对上传字节，再公开；仅同版本、同来源的未公开草稿允许重试补齐，已公开版本不覆盖，修复使用新版本。不要在这些自动草稿中手工添加其他资产。

## 身份与未来商店接入

`chromium-key.json` 保存固定 RSA 公钥，不是密钥或认证凭据。对应私钥由维护者在仓库外备份，不进入源码、CI 或发布包。普通 ZIP 构建只需公钥，不需 Chrome 开发者账号；不要在开发时重新生成公钥。

Chrome Web Store 未来能否承接本地 ID，需要取得账号后在实际条目中确认，当前不承诺无损转换为商店身份。若商店分配不同 ID，可使用上述数据转移路径。版本准备、双浏览器构建和 GitHub 归档不需重做，商店提交只增加消费既有版本产物的步骤。

Firefox 后续签名还需验证 AMO 可独立重建的工作区与公开依赖来源，以及当时要求的数据收集声明和同意流程。签名 XPI 是对同一版本的额外交付物；没有账号时不把未签名包标为商店就绪。当前不配置商店凭据、不创建商店条目，也不声称完成自动更新验收。

实施状态（2026-10-23）：用户随后要求“开始精简”，本节的九项建议已落实到现有实现，而非再次重写架构。配置完整读改和本机保存、地址修正、排除规则回填、登记旁路化、独立后台推进、只读设置和无消费者字段清理、公开正文识别均已修正；同步更新真实使用旅程。InkUI 保留既有视觉语言与内置显隐/ON/OFF，移除表单布局的组件类覆盖；保留必要的白底字段适配与已发布 2.5.0 的一行补丁，不扩展组件分叉。实际运行证据及残余在 [实施接续](implementation-state.md)。下文记录审计当时的发现，不再表示建议尚未实施。

## 2026-10-23 重新评估：产品定位与安全边界

本节是当前审计结论，后文 2026-10-22 内容保留为历史。用户要求重新全面评估，并指出问题是对 InKCre 产品定位、安全边界的误解。本轮只读审查了 WebExt 设置、popup、后台消息、连接、存储、待办、导入、现场采集、公开抓取、阅读、相关 core Peer/数据库接缝、web-collection 全部源码与验收入口；没有修改源码或构建产物。本节建议尚不冒充已经实施或用户接受的新合同。

### 根本判断

InKCre 的目标是让人和工具低摩擦地收集、找到和使用同一 info-base 中的信息，不是构建多租户凭据管理系统。一个部署是一个 owner context；已准入 Peer 在部署信任域内，能力异构而非权限等级。不同传输仍有自己的准入与凭据保管责任。设置页、popup 和后台是同一个 WebExt Peer 的运行分工，不是低权限客户端与高权限服务端。

依据来自 Hub 的 `10-prd/_drivers/business-and-service-objectives.md`、`10-prd/_drivers/operational-realities.md`、`20-product-tdd/security-boundary-model.md`、`system-state-and-authority.md`、`unit-topology.md` 和 `peer-database-runtime-contract.md`。隔离 worktree 未初始化 Hub；本轮从 impl-py/impl-ts 主目录只读核对，两个主目录的安全模型一致。共享文档已明确指出 owner 读取自己的配置不是默认防护对象、凭据持久化不是天然越界、Peer 登记与协议准入不能混为一谈。

上次审计已经写出这些原则，但实现和测试没有贯彻。此次不是补写安全口号，而是撤回错误模型在操作、数据和运行路径中的具体后果。评价从实际 actor、权利、越界路径、发生条件和损失出发；没有生产频率数据，不编造概率，也不把未知风险赋予无限权重。普通编辑每次遇到的阻力是确定成本；不引入第二个主体的“保密”没有相应授权收益。

### 必须修正的正常使用问题

1. **已有配置被当成只能提交、不能读回的秘密。** `runtime.ts:178` 的摘要去除 secret 与 `Options.vue:71–80` 的空值编辑组合，导致每次改名也要重新找密钥。状态摘要不带密钥本身可以只是减少载荷；错误是把摘要作为唯一编辑来源。可信设置页应在打开编辑时读取现有完整本机配置，默认遮蔽并使用 InkInput 显隐，不增加解密、二次登录、一次性取密钥或新授权协议。普通轮询仍可保持轻量。不修正会继续制造复制错误和正常编辑失败，不能用“安全”解释。

2. **真正应保护的 owner 采集意图反而没有正确编辑。** `Options.vue:23、89–98、308–320` 把排除规则编辑值初始化为空，保存则整体替换。已有 A 时输入 B 会丢掉 A；空框直接保存会清空规则。这不是防御机制，而是用户控制失效。应从现有规则开始编辑，追加、删除和取消都反映用户实际改动，刷新状态不能覆盖正在编辑的草稿。通过真实 headless Helium 加载当前产物、写入合成本机配置，已复现 A 被 B 替换；未读取真实资料或密钥。

3. **本机配置保存、联网检测、Peer 登记被捆成一次准入。** `Options.vue:58–69` 与 `runtime.ts:265–279` 让每次修改名称或 PDF 存储也申请连接权限并等待 register/renew 成功。离线或租约错误会阻止与网络无关的维护。普通配置应在输入有效时保存；联网检测和实际连接状态单独报告，失败不能伪称已连接，也不丢待办。密钥更新不应自动生成另一 Peer；若新配置不能工作，owner 能再次编辑恢复，不建设配置版本保险箱。该项是修订此前“联网验证成功才能保存所有配置”的过强承诺，不是保留原承诺却偷偷更改实现。

4. **访问地址被误认为信息库身份。** `Options.vue:211` 禁用地址，`runtime.ts:274–275` 和 `store.ts:117–118` 再拒绝修改。反例是同一信息库换域名、端口或代理路径：另建连接无法修复旧连接绑定的待办。应允许 owner 明确维护同一连接的地址，保留本地连接 ID、Peer ID 和待办；真正加入另一个信息库则仍新建连接。不自动推断两个地址是否同库，也不建设发现、证明或别名注册协议。要明确地址修改会影响该连接尚未发送的工作；不能为了消除这个选择而永久禁止维护，也不能把“单 owner”解释为不同信息库可混写。

### 应移除或收窄的机制

5. **每份材料重复登记和续租，制造了错误的发送门槛。** `outbox.ts:86` 每次调用 `database.ts:22` 新建 WebPeerRuntime；对已有 Peer，core `peer/runtime.ts` 会依次查询、更新登记、续租。每份材料固定多三个请求，任一步失败都阻止随后本来以 JWT 认证的 CRUD。登记和租约表达身份、版本与当前参与状态，不是每份信息的保存许可。应在现有后台生命周期内复用连接对应的 runtime，按生命周期登记/续租，失败单独可见；材料走现有数据库准入。不引入保活平台或守护服务。收益随每次保存和批量导入累积，无须先虚构攻击频率。

6. **后台工作被界面轮询间接驱动。** `runtime.ts:47–55` 一次只做三轮，`ui.ts:12–18、43–47` 每三秒读状态并唤醒；没有 UI 和其他新事件时，后续依赖一分钟 alarm。导入一个含正文的条目已有四个阶段，因此打开设置与关闭设置的调度机会明显不同。这是代码路径结论，本轮未测量吞吐量。UI 应观察工作，不承担推进职责；后台有可执行工作时继续有界批次，遇到暂停、等待或无工作时停止，沿用现有 alarm 恢复。不要为了删阶段破坏已抓取内容的保存，也不要用新的队列框架修补。

7. **对内部状态重复接纳，留下了无收益的写入和身份字段。** `store.ts:86–92` 每次读取 settings 都开写事务、解析后写回，三秒轮询和自动检查都会触发；默认值应只初始化一次，正常读取保持只读。`capture.ts` 与 `collection.content.ts` 的 observation UUID、visible 字段在全树检索中只有生成/传输/校验，没有行为消费者；实际 current 身份已由 profile 和 URL 决定，可以删除这些旧候选残留。保留真实输入、迁移和必要类型恢复处的校验，不能把“简化”变成删除所有 schema。文本/二进制编码和整个本机数据库不因不够短而重做，迁移成本也要计算。

8. **保守取材判断把正常信息误拒绝。** `parse-html.ts:9、17` 只要原 HTML 含 password input，就拒绝已经解析出的正文；一篇带隐藏登录弹层的公开长文因此必定失败。密码输入内容不采集与“整个页面不可采集”是两件事。应以可读正文及实际登录墙表现判断结果，普通登录控件不构成拒绝整页的充分条件，保留对真正无正文/登录页的提示。本轮依据确定分支和构造反例，没有冒充真实网站覆盖率或新的浏览器复现。

9. **UI 与验收仍在迁就实现，而非验证 owner 的完整任务。** 现有 joining 用例每次编辑主动重填 secret，并断言地址禁用，恰好保护了错误流程；按钮显隐测试证明的是新输入值可切换，不是已保存配置可读改。排除规则测试也未走“已有规则继续编辑”。InkUI 的普通页面布局由宿主承担，原生展开区符合组件规范，不能因为要求复用而全部换组件；但 `ui.css:124–135` 的组件类覆盖及 2.5.0 临时补丁仍有维护成本，应优先使用公开组件能力和 token。不能以“保留旧风格”为组件内部覆盖永久辩护，也不能未经授权改造风格或改其他会话的 UI 仓库。

### 收敛顺序与判据

先成组修正配置的读、改、保存、连接检测和地址维护，验证已保存配置默认遮蔽、可显示、只改名称不重输密钥、断网仍可维护，以及修改排除规则保留未动的项。地址修正仍保留同库身份和原待办，新增另一个信息库不接管旧待办。随后从保存热路径移除逐材料注册/续租，把后台推进从 UI 观察中分离，令普通读取没有写副作用；同步删掉无消费者的观察字段。最后收窄误拒绝网页的判断、组件覆盖和测试中的实现绑定。既有可靠性、跨 Peer 普通图和浏览器安全证据只在未改变的边界内复用。

范围是单 owner 的日常浏览与原生批量导入，不按不可信多租户、对抗性已准入 Peer 或多执行者竞赛评估。没有依据要求再次完整重写 WebExt；也不应只补 secret 一行后宣布理解已经纠正。净删行数和性能收益须在实际改动后核算；当前可以确认不需要新增依赖、身份系统、取密钥协议或通用可靠性框架。

本轮新增运行证据只包括隔离 headless Helium 的三个合成 UI 观察：已有密钥未回填、地址被禁用、已有排除规则被新增规则替换。临时 profile 已清理，没有访问日常浏览器、真实密钥或剪贴板，没有调用生产数据库。其他结论来自完整路径阅读及独立 advisor 复核；没有重新运行全量浏览器/数据库验收、生产频率调查或性能压力测试。没有将审计写成已经修复。

## 2026-10-22 历史审计

2026-10-22。本轮审计结论是：**原技术方案不应继续作为实施基线。产品能力范围仍有价值，但 Peer 边界、可靠性目标、状态数量和验收投入需要成套重做，不能只删除一个 RPC。** 本文提出修订建议，不把它们记成用户已经接受的新合同；本轮没有修改源码、运行新的浏览器或数据库测试。

审计覆盖[产品需求](product-requirements.md)、[技术方案](technical-design.md)、[验收与计划](acceptance-and-plan.md)，并核对候选实现的连接、材料 DTO、outbox、导入、DOM 采集、网络获取、旧存储迁移、阅读器和现有 core 接缝。没有审计其他会话拥有的源码。

## 判断基准

当前部署是一个 owner context，已准入 Peers 在同一信任域内，运行能力可以不同。网页内容仍是不可信数据。不能套用多租户、对抗性 Peer 或集中式后端的默认模型。

投入应比较“机制能够减少的预期损失”与“开发及交付延误、依赖、维护、迁移和新增故障成本”。预期损失至少取决于使用暴露量、事件发生概率、后果以及检测和恢复代价。没有实际频率数据，本审计不编造概率，也不把概率未知理解为高风险或零风险。故障注入证明可发生与机制有效，不证明其发生率和 ROI。

已有依据不是新发明的简化口号：

- `impl-py/tasks/knowledge-lifecycle-capabilities/decisions/D111-D120.md` 的 D-117 区分平等权威和异构执行，拒绝把检索业务放进数据库 RPC；字节传输原语不为业务 SQL 提供普遍先例。
- 同任务 D-376 不为低概率跨语句读取竞态增加数据库业务 RPC、Serializable 事务或快照 token。
- `architecture-understanding/authority-lifecycle.md` 的 U-037/U-044 同时衡量错误损害、可检测性、恢复拓扑和并发机制成本，不因理论 race 自动建设 exactly-once。
- `impl-ts/tasks/peer-extension-experience/packet.md` 已有单用户 best-effort 删除清理的实际取舍，明确没有为并发边缘情况增加数据库 RPC。
- 共享 `security-boundary-model.md` 要求具体 actor、资产、边界、攻击路径和成比例控制，不以“安全”一词替代收益判断。

## 需要改变的设计

### 1. Peer 独立性被替换成了“浏览器必须包办全部能力”

原方案第 7、121、148 行要求不启动 Python/Mac，只留数据库，完成整条核心旅程；同时为了满足这一判据，把网页业务实现下沉为数据库 SQL。产品要求的是 WebExt 不依赖 client-web 的源码、页面、会话或代理，并允许按能力委托其他 Peer，不是所有能力只能由浏览器独自实现。

这项成本是确定的：本地执行器、平台解析环境和数据库专用操作都被独立性验收推成必选项。它没有对应的故障概率收益；这是边界和实现自由被错误收紧。

**建议修订：**WebExt 拥有自己的身份、连接、交互和浏览器现场能力。能本地实现的业务直接执行，需要其他执行能力时使用既有精确能力或 Source/Job 合同，不绑定应用名称或固定节点。保留简单直接的浏览器保存路径，但不把“其他运行时全部关闭”当作所有旅程必须满足的架构定义。也不反向把普通保存改成必须寻找 Python Peer。

### 2. 网页业务 RPC 与强制数据库升级违反既有职责边界

原方案第 63、69–84、134 行新增 `submit_web_material_v1`、`read_web_material_v1`、回执表和协议版本。候选 `logic/collection/database.ts` 在连接时强制检查两个 RPC；SQL 解释来源、current/fixed、HTML/PDF、附注和修订，而不是只传输不透明字节。

每个使用者必然承担数据库兼容升级成本，网页合同变化还会传播到迁移、准入、生成投影、锁与并发测试。避免偶发重复、半份材料或读取混合修订的收益尚未按损害和频率证明。技术上可以调用，不等于应由数据库执行；“所有 Peer 都能调用”也不能消除这个问题。

**建议撤回这两个领域 RPC、专用回执表和强制准入依赖作为方案要求。**网页构图和解释归 Peer 中的 Collection/Resolver 实现，使用现有协议。不立即用通用事务 DSL、幂等平台、暂存发布或补偿框架替代它们。现有 CRUD 不能提供相同的全局强保证；应明确重定保证，而不是改名后继续购买同一套机制。

### 3. 可靠性被当成一种统一的、必须最大化的属性

原方案第 71–78、149 行与验收表“一次逻辑接纳”把全有或全无、相同请求永不重复、删除后永久防复活、current CAS 和同快照读取同时定为完成条件。这些后果并不等价。

| 情况                                  | 发生依据与概率边界                                       | 实际损失及恢复                                                       | 本轮合适的投入                                                                                 |
| ------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| worker 退出或浏览器重启，内存待办消失 | worker 非常驻是已知平台行为；有待办时不能依赖内存        | 登录页现场、选区或附注可能不能重建                                   | 保留本机持久待办和有限批次恢复                                                                 |
| 切换连接后旧材料写进新库              | 操作路径明确；错误设计会让队列项读取新全局连接           | 私人材料错投，且难以自动撤回                                         | 入队绑定原目标；发送时不用当前连接替换                                                         |
| 自动刷新覆盖用户主动原文或附注        | 自动更新与主动保存组合就是正常用法                       | 用户表达和历史原文可能不可恢复                                       | 分开可变与主动保留内容，不共用可变字节                                                         |
| 数据库已成功而响应丢失，再次创建      | 需命中“已提交、未收到确认、随后重试”的组合；无实际发生率 | 可能重复材料、额外索引和整理成本；不等同于原文丢失                   | 本地串行、已知 ID/来源事实的检查和阶段恢复；接受显式 best-effort 残余，不承诺全局 exactly-once |
| 图与字节写到一半中断                  | 多请求路径可以发生；无实际发生率                         | 局部残缺、孤儿字节、需要继续保存；是否丢失原文取决于本机载荷是否保留 | 保存已知阶段和 ID；失败不谎报成功，保留待办；不先建通用回滚/垃圾回收系统                       |
| 普通 LIVE 阅读恰遇另一修订            | 需读写时间重叠；无实际发生率                             | 一次预览可能混合或缺少部分内容，重新读取可恢复                       | 普通读取及局部缺失处理，不为此加网页专用快照 RPC                                               |
| 来源内容取得凭据或被执行              | 有具体消息、网络或渲染边界；不能拿低概率作为忽略理由     | 密钥泄露或执行不可信代码，损害远大于重复记录                         | 复用平台与现有库的认证、消息校验、纯数据呈现；不另造安全框架                                   |

这里的“best-effort”不是把失败吞掉：已确认本机留存和已共享保存必须区分，失败保留信息并给出可用处理入口。不能把我在产品提案中写出的绝对恢复语句反过来当作基础设施的授权来源。产品需求中“重试不会产生重复资料”等绝对表述需要显式修订，不应静默声称原承诺仍被兑现。

### 4. 为尚未存在的跨执行者导入建设了恢复协议

原方案第 115–125 行同时设计本地枚举检查点、outbox、共享 Source 检查点、Job 尝试、运行世代、CAS 和旧执行者排除。当前实现只有浏览器本地 runner，没有同一批次在多个执行者间转移的真实路径。

本地恢复解决扩展会被挂起的现实问题，收益成立；跨执行者争写风险则要先由未来的执行权转移功能制造出来。为未提供的功能先建设协调协议，新增成本却作用于每个普通导入。

**建议收窄为每次导入一个明确执行 owner。**本机保存范围、未完成项和必要进度，重开继续；单条失败不阻断其他条目。具体服务确实使用 Source/Job 时沿用其合同，不在网页核心方案里先重做通用执行权转移。取消停止剩余工作，已经派发的效果不保证撤销；已导入资料不删除。远端续跑能力在真实连接器和使用场景成立后再设计。

### 5. 严格身份证明把不确定误覆盖换成了正常路径的重复积累

原方案第 55–57 行及 `collection.content.ts` 为每次导航或文档重建生成新观察 ID。重开同一篇文章，即使内容没变，也不能跨访问复用。这不是偶发失败：重复访问是产品正常用法，规则本身会持续产生新根和正文。

同 URL 不同账户、公开抓取与登录现场不应被粗暴合并；但其发生频率和误覆盖损失尚未与重复量、检索噪声及存储成本比较。“允许重复”不是完整成本判断，不能把整理责任全部移给 Organization。

**建议把跨访问复用作为有界、best-effort 的业务策略重新决定，而不是要求证明账户与来源绝对连续。**不粗剪 query/SPA 路径，不让自动更新触碰主动材料，来源原生 ID 仍优先。先用实际页面重访、内容变化和同 URL 切账户样本判断；不建设通用账户识别、身份注册或版本证明系统。现有保守策略可以作为无法判断时的退化，但不能不计算其正常重复成本。

### 6. 统一材料模型制造了更多写入阶段，又用阶段数量论证原子事务

原方案第 43–53 行普遍采用来源根、材料根、多个语义叶子和归属关系。书签或服务收藏有独立身份和生命周期，单独表达有价值；一次选区或普通手动保存不一定都需要同样多的包装。

每多一个必须协调的对象，就新增写入、查询和残缺状态，继而形成“必须用事务”的循环论证。方案还把浏览器来源记录 JSON、持久 `sources` 的操作配置及观察对象混用为“Source”，使责任不清。

**建议逐个对象按独立用途决定是否存在。**保留实际正文、出处、用户附注的区别，沿用现有 core 语义 Resolver 与 Storage；不要为追求最少节点把全部内容塞进另一套 JSON 文档库。普通保存不强制建立 Source/Job；需要独立更新、查询或复用的书签/历史事实再独立表达。

同时，候选 `packages/web-collection` 只有 DTO 和 RPC 客户端，未实现两个自定义根的 Resolver；标准语义叶子可读，不等于根上的出处与材料关系已经能被其他 Peer 解释。**“扩展关闭后信息仍可使用”比“所有对象同事务写完”更接近产品价值，应优先补齐最小跨 Peer 解释闭环，而不是继续扩写写入证明。**无需为此立即发布多种 Extension Distribution。

### 7. 本地持久化值得保留，但未区分自动与主动工作的价值

原方案第 86–95 行的持久待办、目标绑定、容量上限与暂停检查有直接价值。过重的是让所有自动观察承担与主动摘录相同的交付债务，并让回执成为整个队列的核心状态。

候选实现还暴露一个普通调度问题：`outbox.ts` 先取前三项再检查暂停。当队头至少三条自动项被暂停时，后面的手动保存始终得不到发送机会。这是满足条件后确定发生的阻塞，不需要分布式竞争才能触发。`enqueueCapture` 也不是方案中承诺的未发送自动变化合并，而是有待处理项就暂时拒绝新观察。

**建议保留最小本机队列，按工作价值安排发送。**手动保存不能被暂停的自动项挡住；未发出的同一自动观察可合并为最新状态。不增加多套队列、复杂调度器或 retention 服务。若要淘汰已经确认接纳的自动材料，须明确改变原产品承诺；本审计不授权静默淘汰。按真实容量选择有界默认值，不把候选 200 项、128 MiB、32/48 MiB 误写成用户需求。

### 8. 安全目标导致正常取材退化，部分共享机制又被重写

`fetch.ts` 对不携带 InKCre 认证的公开网页请求也使用 `redirect: 'error'`，遇到 HTTP→HTTPS、地址迁移或常见跳转就失败；HTML 只接受 UTF-8。受影响比例没有样本，但只要遇到这些输入就确定失败。数据库携带认证请求的目标约束，不能不加区分地套到公开原站取材。

`database.ts` 自写带认证的 JSON fetch，尽管 core 的 `DBAPIClient` 已支持绑定 base URL 和 token provider；原始字节接缝才有仍依赖全局 authStore 的实际限制。`legacy-storage.ts` 为全部旧 key 重做 IndexedDB KV、迁移删除和 BroadcastChannel，而非只处理敏感连接与大载荷。

**建议收窄到具体边界。**保留公开抓取不带账户凭据、不转发 InKCre JWT、检查特权消息以及不执行来源内容；公开网页的普通重定向和编码应通过现有网络/解析能力处理，不先设计通用代理或 URL 安全平台。关系/JSON 查询优先复用连接绑定的 DBAPIClient；字节接口若需精确连接，只补那个窄接缝。

Chromium 原生 storage 已有 `setAccessLevel`，因此“内容脚本不能读配置”不能自动推出“所有旧数据必须迁入自造 KV”。Firefox 与现有旧页面的实际访问仍须核对，不能机械选 Chromium-only 控制；敏感配置和大载荷可以合理留在扩展源 IDB，而无关旧偏好不必连带改写。

### 9. 页面覆盖和阅读承诺超过证据，但真实核心能力仍未闭环

原方案第 103 行把“验证 frame 是否承载正文”升级为各 frame 独立观察并聚合来源和时间。现实现只接受顶层消息、注册 `allFrames: false`，能读的只是同源可访问 frame；没有已授权跨域 frame 聚合。应先验证实际目标页面的内容损失，再补必要覆盖，而不是为任意网页建聚合系统；真实主体缺失仍须明确提示。

静态打包、Chrome 的 DOM 解析环境和不执行保存脚本有实际平台依据，不能因为审计复杂度就一并删除。已有 Readability 与有限 offscreen 接缝可以复用，不需要完整富文本浏览器、页面镜像或新动态扩展发行系统。文字阅读、出处、HTML 源码及 PDF 原始内容已经是可用首轮体验；`InfoBaseRouter` 绑定不是独立阅读的唯一合格实现。

更需要优先处理的是确定性功能断点：后台返回 `{ok:true,value:{allowed:true}}`，`collection.content.ts` 却读顶层 `allowed.allowed`，所以自动观察无法进入采集分支。当前两项扩展测试覆盖装载和手动故障恢复，没覆盖自动、书签/历史或 PDF。这表明测试投入围绕强机制，而不是核心旅程。

平台适配也有明确欠账：`fetch.ts` 直接调用 `offscreen.hasDocument()`，官方当前标明该方法为 Chrome 150+，manifest 没有相应 Chromium 最低版本声明。应决定实际支持范围或复用已有可用检查，而不是拿类型检查/构建当兼容证据。Firefox 构建通过亦不等于运行通过。

### 10. 迁移与验收应保护真实用户价值，不替不存在的合同背书

原方案第 138–155 行保留原数据、旧地址不猜成 PostgREST、未知旧待办不批量重放，这些是合理的低成本选择。应核实实际存在的旧配置和待办，再写对应迁移，不先建设多版本迁移框架。Explain/Writing Assist 的入口和原始数据不能静默消失，但不因此把所有旧执行方式永久保留，或者顺带重写成另一套 AI/查询产品。

验收中的独立身份、真实材料读回、来源时间区分、主动材料稳定、暂停/排除、混合导入、重启恢复和双浏览器行为仍有价值。应撤掉“所有故障只能完整一次接纳/回滚/冲突”“普通读取必须同快照”等实现强绑定判据；不把新方案允许的 best-effort 残余继续判成失败，也不在删机制后保留其专属证明矩阵。

保留一小组能区分实际损失的检查，先真实常用页面、重复访问、主动选区/附注和混合导入，再检查一次中断恢复、目标切换、取消和真实权限。平台权限不能完全由预授予 fixture 代替；既有人工授权证据与自动化数据路径证据分别使用，不重复大量原生 UI 操作。

## 修订验收与后续工作

新方案应围绕三个闭环组织，而非围绕数据库协议组织：

1. 浏览器现场、选区或 PDF → 明确目标 → 保存实际材料及出处 → 在扩展和另一具备解释能力的 Peer 读回。主动附注与原文不会被自动刷新改写。
2. 授权浏览与 SPA 变化 → 有界自动观察 → 当前可用材料。重复访问量、页面完整性、暂停与手动优先级在真实样本里判断，而不是只验证 revision/CAS。
3. 书签/历史预览 → 来源事实与当前内容 → 单项失败保留记录 → 停止、重开、只重试未完成项。浏览器关闭时不伪称仍在执行，且不以跨 Peer 执行权转移为前置条件。

最小判别样本是：同一静态文章重开多次；一个正文动态变化的 SPA；同 URL 切账户；含普通页、跳转、登录页和失效页的一批书签/历史；一份有用的在线 PDF；一项尚未发送时中断和一项结果未知的保存。它们分别揭示重复量、误覆盖、正文成功率、失败恢复成本和真实边界。没有这些观察前，不宣称生产概率、定量 ROI、复杂 frame 覆盖或 Firefox 行为已经成立；也不为估计低价值风险先建遥测平台。

下轮应先修订技术方案及其产品绝对语句、验收判据与计划，再在已有授权范围内处理源码；不能一面保留旧强判据，一面声称新方案已简化。本轮审计没有执行撤回、迁移、测试删除或源码修复。现有候选变更仍在工作区，清理时只处理本任务内容，不动 Capture、Organization、query/sinks、Mail 等其他所有者的变更。

## 证据入口与边界

- 原方案定位以上述审计前的行号为准；文首增加审计状态提示后可能顺延。
- `packages/core/src/base/db-api.ts` 的 DBAPIClient 构造参数支持独立 base URL/token provider；`peer/runtime.ts` 的 `forConnection` 已使用该接缝。
- `apps/client-webext/logic/collection/database.ts` 的 RPC/Storage 准入、`store.ts` 的持久化和容量、`outbox.ts` 的发送候选选择、`imports.ts` 的本地阶段是本轮代码证据。
- `packages/web-collection/src/index.ts` 当前为 schema 与 RPC 客户端；未发现对应自定义根的 Resolver 注册。`runtime.ts`、`collection.content.ts` 与 `background.ts` 证明自动消息返回结构不匹配，尚未运行修复测试。
- [Chrome worker 生命周期](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)说明 worker 退出与内存变量丢失；这支持本机持久化，不支持业务 SQL。
- [Chrome Storage](https://developer.chrome.com/docs/extensions/reference/api/storage)说明 `storage.local` 的访问级别控制；不能据此假设 Firefox 行为相同。
- [Chrome 远程代码限制](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code)支持随包执行代码；[offscreen API](https://developer.chrome.com/docs/extensions/reference/api/offscreen)支持 DOM 解析用途，并标明 `hasDocument` 的版本限制。平台事实于本轮核对，不扩展成浏览器兼容全审计。

未取得真实使用频率、用户资料规模和代表性网页样本；未新跑浏览器、性能、迁移或数据库验收。本报告是技术方案及关联实现路径的审计，不是源码整体质量审计或实现完成证明。
